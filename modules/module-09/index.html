Non-Functional Requirements & Validation

Learn to identify and classify non-functional requirements, and understand how we validate that all requirements are complete, consistent, clear, correct and realistic.

📖 4 sections 🎯 10 quiz questions ✏️ 3 exercises ⏱ ~35 min
1

What are Non-Functional Requirements (NFR)?

Kenneth opens with a key definition: «A non-functional requirement places a constraint on a use case, or on the system as a whole.» It is not a functionality the system performs — it is a constraint or quality property that applies to the functionality.

Think of it this way: the requirement «The system shall allow users to register» is functional. But «The system shall respond to all requests within 2 seconds» is a constraint on all functionalities — that is an NFR.

NFR vs Functional Requirement

Functional requirement: What the system does — a specific functionality. Captured in the use case model.

NFR: A constraint on how the system does it, or a system-wide property. Placed in a separate section of the SRS.

Kenneth divides NFRs into the following categories. All examples are from the SetWatch lecture:

Kategori Underkategori SetWatch-eksempel
Design quality Reliability «As SetWatch has no battery, no software fault requiring the resetting of the watch should occur.»
Design quality Supportability «SetWatch should accept upgrades to its onboard processor via USB interface.»
Performance Response time «SetWatch should display the correct time zone within five minutes of the end of a GPS blackout period.»
Performance Accuracy «SetWatch should measure time within one of a hundredth second over five years.»
Implementation Language/standards «All related software associated with SetWatch will be written using Java.»
Interface External system «SetWatch complies with the physical, electrical and software interfaces defined by Webify Watch API 2.0.»
Interface Usability «Any user who knows how to read a digital watch and understand international time zone observations should be able to use SetWatch.»
Security System/data/physical Constraints on who can access the system, the data, or the physical device.
Hardware Memory/storage Requirements for memory size, storage capacity, and implementation platform.
Documentation What & for whom What documentation is needed, and for whom (users, developers, operators)?
NFR as Administration Use Cases

Kenneth points out that some NFRs — especially security and operational requirements — are implemented as dedicated administration use cases. Examples: login, system startup, system shutdown, system backup. Kenneth: «Administration use cases are use cases that deal with non-functional requirements, for example security, or system operation or maintenance.»

Requirements Validation — the Five Criteria

Once all requirements have been captured (domain model, use case model, NFR) they MUST be validated continuously with the client or user. Kenneth: «All the requirements that we have captured in the SRS should be validated continuously with the client or user.»

SRS — What Makes a Complete Requirements Specification?

Kenneth closes module 9 with a summary of what a complete System Requirements Specification (SRS) must contain. This is the requirements package delivered to the client and used as the basis for design and implementation.

SRS — Three Parts

Domain Model

  • Captures data requirements
  • Represented as a class diagram
  • All important objects and relationships in the application domain

Use Case Model

  • Captures functional requirements
  • Use case diagram — overview of all functionalities
  • Use case specifications — flow of events for each use case

Non-Functional Requirements

  • Captures constraints and quality properties
  • Design quality, Performance, Interface, Security, Implementation, Hardware, Documentation
  • Some are implemented as administration use cases
Kenneth: «In our SRS we should have a domain model, a use case model, and also all the non-functional requirements.»

Acceptance Tests — the Primary Validation Mechanism

Once the SRS is complete, acceptance tests are used to validate that the finished implementation actually satisfies the requirements. Kenneth: «Acceptance tests are the primary means to validate the system implementation satisfies the requirements. In acceptance tests, we try to validate all the requirements in front of our client or user.»

The Lifecycle Going Forward

Kenneth explains what happens after the SRS: «In the subsequent iterations or phases, we will find and also transform the requirements by specifying more details. We should come up with a matching use case realization in the analysis model, and also a matching use case realization in the design model. And we're going to use the analysis model and also the design model for implementation.»

The SRS is therefore the starting point for all further development — not an isolated document.

Ex 1

Classify the requirements — functional or NFR?

▾

For each requirement: decide whether it is a functional requirement (FC) or a non-functional requirement (NFR). If NFR, state which category (reliability, performance/response time, performance/accuracy, supportability, interface/usability, implementation, security, documentation, hardware).

  1. «The system shall allow users to search for books by title, author or ISBN.»
  2. «Search shall return results within 1 second for databases of up to 1 million books.»
  3. «All source code shall follow the Google Java Style Guide.»
  4. «The system shall send email notifications to users for overdue loans.»
  5. «The system shall not permit unauthorised access to borrowing history.»
  6. «The system shall handle 500 concurrent users without performance degradation.»
  7. «The system shall provide an installation guide for IT staff.»
Solution
  1. FC — This is a concrete functionality (search) captured in the use case model.
  2. NFR — Performance (response time) — Places a time constraint on the functionality.
  3. NFR — Implementation — Sets coding standards and programming conventions.
  4. FC — Concrete functionality (sending notifications). Will be modelled as a use case.
  5. NFR — Security — Access control is a security constraint. Can be implemented as an administration use case (login).
  6. NFR — Performance (throughput/capacity) — Places a capacity constraint on the system as a whole.
  7. NFR — Documentation — Defines what documentation is needed and for whom.
Ex 2

Find the validation flaw — which type is it?

▾

For each requirements example: identify the validation flaw (Incomplete, Inconsistent, Unclear, Incorrect, Unrealistic) and briefly describe what is wrong and what the solution is.

  1. «The system shall send SMS notifications to users.» — but there is no requirement about what the SMS should contain, when it should be sent, or whether users can opt out.
  2. «The system shall not store personal data.» and «The system shall store user preferences and purchase history to personalise recommendations.»
  3. «The system shall handle payments.» — but it is unspecified which payment methods, currencies, or whether refunds are included.
  4. «The system shall respond to all queries within 0.000001 seconds» for a web-based system.
  5. «The system shall support all 193 UN member states» — but the actual list of supported countries elsewhere in the spec is limited to G7 countries only.
Solution
  1. Incomplete. The requirement describes a function but does not specify content, trigger condition, or user opt-out. Fix: add requirements for SMS content, when it is sent, and how to disable it.
  2. Inconsistent. The two requirements directly contradict each other. It is impossible to satisfy both. Fix: revise one — e.g. allow storage of preferences without storing personally identifiable information.
  3. Unclear (+ Incomplete). «Payments» is a vague term. Fix: specify which methods (Visa, PayPal, ApplePay?), currencies, and whether refunds and partial payments are in scope.
  4. Unrealistic. 1 microsecond response time is technically impossible for web-based systems with network latency. Fix: set a realistic requirement based on actual infrastructure.
  5. Incorrect + Inconsistent. The 193-country requirement contradicts the implemented country list elsewhere. Fix: correct one of the two to match what is actually possible and desired.
Ex 3

Write NFRs for a mobile payment system

▾

Du jobber med kravinnsamling for et mobilbetalingssystem (som Vipps eller PayMe). Skriv ett NFR for hver av de følgende kategoriene. Hvert krav skal være konkret, målbart og ha tydelig kategori.

  • a) Performance — Response time
  • b) Design quality — Reliability
  • c) Security
  • d) Interface (ekstern system)
  • e) Implementation
Eksempelløsning (andre svar er mulig)
  • a) Performance — Response time: «En betalingstransaksjon skal bekreftes eller avvises innen 3 sekunder under normale nettverksforhold.»
  • b) Reliability: «Systemet skal ha en oppetid på minst 99,9% per måned. Planlagt nedetid skal varsles 24 timer i forveien.»
  • c) Security: «All kommunikasjon mellom mobilklient og server skal krypteres med TLS 1.3 eller nyere. Betalingsdata skal aldri lagres i klartekst.»
  • d) Interface: «Systemet skal samsvare med PCI DSS v4.0 for behandling av kortbetalinger.»
  • e) Implementation: «Backend-tjenester skal implementeres i Kotlin med Spring Boot. iOS-app i Swift, Android-app i Kotlin.»

Legg merke til at gode NFR-er er spesifikke og målbare — «innen 3 sekunder», «99,9% oppetid», «TLS 1.3» er langt bedre enn «rask», «pålitelig», «sikker».
