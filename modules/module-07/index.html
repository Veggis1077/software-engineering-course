Module 07

Use Case Modeling

Learn to identify actors, formulate use cases and draw use case diagrams — following Kenneth's walkthrough with ASU Course Registration as the running example.

📖 5 sections 🎯 10 quiz questions ✏️ 3 exercises ⏱ ~35 min
1

What is use case modeling?

The use case model captures functional requirements from the user's perspective — "what the system shall do", seen from outside. While the class diagram (modules 2–3) answers "what data do we need", the use case diagram answers "what functions does the system provide?".

Kenneth explains it this way: «In use-case modeling, we try to capture the system behavior from the user's point of view.» Use cases drive the entire development process — you implement the system based on the functionalities captured in the use case model.

Captures

Functional requirements — what functions the system provides, from the actor's perspective.

Developed

Incrementally, in parallel with the domain model. Used to plan development iterations.

Validates

Helps validate that requirements are correctly understood — stakeholders can read and verify.

A use case is a UML class

Just as a class classifies objects, a use case classifies scenarios. A use case is a stereotype of a UML class. A scenario is an instance of the use case — just as an object is an instance of a class. Kenneth: «We classify all the instances together as a single use case.»

2

Actors — who interacts with the system?

The first thing you must include in a use case diagram is the actors. Kenneth defines it this way:

Definition

An actor represents something outside the system that interacts directly with the system. An actor can be a person or another system. It provides input to or receives output from the system.

✓ Always an actor
  • People (student, instructor, administrator)
  • External systems (billing system, bank API)
  • Time / event triggers (scheduler)
✗ Never an actor
  • Input/output devices — keyboard, mouse, printer
  • Internal system components
  • The database the system uses internally
Important: one role, not one person

An actor specifies a role — not a concrete person. Kenneth: «We may have multiple roles per user or multiple users per role. That means a user can do multiple things on the system, and also different users can do the same thing.»

Example: John Smith can hold the role of Student and Teaching Assistant at the same time. That gives two actors but only one person.

Actor in domain model AND use case diagram

Kenneth makes an important point: the same concept can appear both as a class in the domain model and as an actor in the use case diagram. They play different roles:

Student in Class Diagram

Represents data we need to track in the system — the student's name, ID, which courses they are enrolled in.

Student as actor

Represents the role of a user interacting with the system — the student who logs in and registers for courses.

How to identify actors

Ask yourself these questions when reading the problem statement:

  • Who or what will use the system?
  • What roles do they play in the interaction?
  • Who provides and receives information from the system?
  • What other systems communicate with it?
  • Who installs, starts, stops or maintains the system?
From the lecture's ASU example

Kenneth reads the problem statement sentence by sentence and identifies: Student (registers for courses), Instructor (selects courses to teach, requests student list), Billing System (external system that receives billing info). Through analysis of who "prepares course offerings" and "cancels course offerings", a fourth actor is discovered: Registrar (administrator who maintains course information).

3

Use Cases — functionality from the actor's perspective

A use case is a specific way of using the system — one functionality from the actor's perspective. Kenneth: «A use case describes the interaction that takes place between an actor and the system, and what the system must do from the actor's perspective.»

Characteristics of a use case:

  • Always initiated by an actor — a use case never starts by itself
  • Complete sequence of events and actions — a whole story, not a fragment
  • Starts with basic flow (normal path) — alternative flows added in use case specification (Module 8)
  • Uses vocabulary from the application domain

Use case vs scenario

Use Case (the class)

General description of a functionality — for all users in this role. E.g. «Register for Courses»

Scenario (the instance)

One specific user's attempt to execute the use case. Kenneth: «Kenneth is using the system to do something.»

Naming — correct and incorrect

Use cases are named from the actor's perspective, using a present tense verb in active form. Kenneth is explicit about this.

✓ GOOD NAMING
  • Register for Courses
  • Maintain Course Information
  • Select Courses to Teach
  • Request Enrollment List
✗ BAD NAMING
  • Course Registration (noun)
  • Student registers courses (wrong tense)
  • Add/Drop Function (technical)
  • Process enrollment (not actor perspective)

How to identify use cases

  • What tasks does the actor want to perform on the system?
  • What information does the actor want to retrieve from the system?
  • About what external events must the actor inform the system?
  • About what events will the actor be notified by the system?
  • How will the system be supported and maintained?
The most important rule — Kenneth's golden rule

«A good use case typically represents a major piece of functionality that is complete from beginning to the end. It has to be a complete story from beginning to end.»

Kenneth demonstrates with the ASU example: «select course offering», «add course», «drop course» are not good use cases on their own — they are fragments of a larger story. The complete story is: «Register for Courses».

«It is better to have longer and more extensive use cases than smaller or partial ones.»

Arrow vs line — the most common exam trap

This is one of the most frequent errors on exams. Kenneth explains it carefully with the Billing System example:

→ Arrow from actor to use case

Means: the actor initiates the use case. The actor starts it.

E.g. Student → Register for Courses. The student starts the registration.

— Plain line (no arrow)

Means: the actor communicates with the use case but does not initiate it.

E.g. Billing System — Register for Courses. Billing System receives info, but Student initiates the use case.

Kenneth's exact explanation

«We have a link, a line between Register for Courses and the Billing System. Because within the Register for Courses use case, eventually you're going to receive billing information. So that's why we have a line here — that means there will be some communication between the Billing System and the use case. We don't have an arrow. That means this use case is not started by the Billing System. It's actually started by the Student.»

Generalisation — on actors, not use cases

You can use generalisation on actors (e.g. Employee generalised into SalesClerk and Manager). However, Kenneth warns explicitly: «Try not to use use case generalization in your project. It is often used incorrectly. I suggest you try to avoid using generalization on use cases.» — Use it on actors, not on use cases.

Complete example — ASU Course Registration

Kenneth walks through this example step by step in L7-3. It is the primary example for use case modeling in the course. Here is the full process:

Step 1 — Read the problem statement, identify partial functionalities

Kenneth reads the problem statement sentence by sentence and extracts partial functionalities:

From problem statement Partial functionality Actor
Students request course catalog Browse course offerings Student
Someone prepares course offerings Prepare course offerings ? (→ Registrar)
Students select course offering / indicate alternatives Select course offering Student
Someone cancels course offering Cancel course offering ? (→ Registrar)
Billing system receives billing info Receive billing information Billing System
Instructor selects courses to teach Select courses to teach Instructor
Instructor requests enrollment list Request enrollment list Instructor
Student adds / drops course offering Add course offering / Drop course Student

Step 2 — Group into complete use cases

The list above cannot be used directly — too many fragments make the diagram unreadable. Kenneth groups them:

Browse courses + Select course + Add course + Drop course → Register for Courses Student

Kenneth: «They are trying to register for courses. So we group all these functionalities and make one single use case.»

Prepare course offerings + Cancel course offering → Maintain Course Information Registrar

The Registrar maintains course information — a complete story from beginning to end.

Select courses to teach Instructor and Request enrollment list Instructor → kept separate

These two are different enough to be kept as separate use cases — they represent different complete stories.

Ex 1

Identify actors and use cases — Library system

▾

Problem statement:

"A library system allows members to search for books, borrow books, and return books. Library staff can add new books to the catalog and remove books. An external fine calculation system calculates overdue fines and sends them to the library system. Members can also reserve books that are currently on loan."

  • a) Identify all the actors. Explain the role of each.
  • b) Identify all the use cases. Give them good names.
  • c) Which actors use an arrow (initiates) and which use a plain line?
Solution

a) Actors:

  • Member — person who registers as a library user and borrows books
  • Library Staff — employee who manages the book collection
  • Fine Calculation System — external system that calculates fines

b) Use Cases:

  • Search for Books — Member searches the catalog
  • Borrow Book — Member borrows a book
  • Return Book — Member returns a book
  • Reserve Book — Member reserves a book currently on loan
  • Manage Book Catalog — Library Staff adds and removes books (group add + remove)
  • Process Overdue Fines — system receives and handles fine information

c) Arrow vs plain line:

  • Member → (arrow) Search, Borrow, Return, Reserve — Member initiates all of these
  • Library Staff → (arrow) Manage Book Catalog — Staff initiates
  • Fine Calculation System — (plain line) Process Overdue Fines — the system communicates/sends data, but an internal event or schedule initiates the process, not the external system
Ex 2

Are these good use cases? Apply Kenneth's rule

▾

For each proposal: is it a good use case? Apply Kenneth's rule: «A good use case is a complete story from beginning to end.»

  • a) «Click Submit Button» (online shop)
  • b) «Place Order» (online shop — includes browse, add to cart, enter payment, confirm)
  • c) «Enter Password» (banking system)
  • d) «Transfer Money» (banking system — includes login, select account, specify amount, confirm, receipt)
  • e) «Course Registration» (course registration system)
  • f) «Register for Courses» (course registration system)
Solution
  • a) Not good — «Click Submit Button» is an action, not a functionality from the actor's perspective. It is a fragment of a larger use case.
  • b) Good — «Place Order» is a complete story from beginning to end. The actor wants to order — and the entire process is represented.
  • c) Not good — «Enter Password» is one step in an authentication flow, not a complete functionality. Is it a start? Is it an end?
  • d) Good — «Transfer Money» is a complete, meaningful transaction story.
  • e) Bad name — «Course Registration» is a noun. Use cases should be named with present tense, active form: «Register for Courses».
  • f) Good — Correct name (verb, present tense, actor's perspective) and represents a complete functionality.
Ex 3

Draw a use case diagram — Online Banking

▾

Problem statement:

"An online banking system allows customers to view their account balance and transaction history, transfer money between their own accounts, and pay bills. Bank employees can open new accounts and close existing accounts. An external credit scoring system periodically receives customer data from the banking system to update credit scores."

  • Identify the actors and use cases
  • Sketch the use case diagram (describe it in text or draw it): system boundary, actor placement, correct use of arrow vs plain line
Solution

Actors: Customer, Bank Employee, Credit Scoring System (external)

Use Cases:

  • View Account Summary (Customer) — balance + history is one complete functionality
  • Transfer Money (Customer)
  • Pay Bill (Customer)
  • Manage Accounts (Bank Employee) — open + close grouped as one use case
  • Update Credit Score (internal process, triggered periodically)

Diagram notation:

  • Customer → (arrow) View Account Summary, Transfer Money, Pay Bill — Customer initiates
  • Bank Employee → (arrow) Manage Accounts — Employee initiates
  • Credit Scoring System — (plain line) Update Credit Score — the system receives data, but an internal event/schedule triggers the process, not the external system
