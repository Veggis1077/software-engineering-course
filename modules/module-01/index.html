Why is software complex to develop?

Kenneth opens the course by establishing one fact: large software systems contain an enormous amount of code, and this alone makes them impossible to manage line by line. A Boeing 787 has 14 million lines of code. Windows 10 has 50 million. A modern game typically has 6 million.

From the lecture (L1-3 — Apple engineer)

«Boeing 747 has more lines of code than it does parts — including nuts and bolts. I was really blown away when I heard this. At 1 line of code per minute, 40 hours per week, 50 weeks per year, one engineer can produce 120,000 lines of code per year. For a 2 million line project, you need at the very least 17 software engineers. You get a feeling that these things need to be planned out a lot and that you have to work in teams.»

Consequences of poorly managed complexity

Unmanaged complexity leads to real disasters. Kenneth highlights two concrete examples:

Ariane 5 (1996)

A European rocket exploded 37 seconds after launch due to one small software bug. The rocket cost hundreds of millions of dollars. Kenneth plays footage of the actual explosion in the lecture. «The entire rocket just blew up because of a tiny mistake in the software system.»

London Ambulance (1992)

London's ambulance dispatch system failed twice in 1992. People died because ambulances did not arrive. The system was classified as «unsafe» — a direct result of a failed software implementation in a safety-critical domain.

Amazon.com — $2.8 million in 90 minutes (L1-3)

«The software team was going to do one small software upgrade. Pretty easy. But the upgrade didn't go out so hot and it caused a 90-minute outage. The estimated cost to Amazon was $2.8 million in lost revenue. This team needed a better understanding of the process for developing a critical system and how to bring an upgrade online without taking down the system.»

The system was not safety-critical — but it was financially critical. Lack of process cost them dearly.

Statistics — industry figures Kenneth uses

45% of software projects are over budget
7% are delivered late
56% deliver less value than promised
17% are «company threatening» — endanger the business
2

Dealing with Complexity — three techniques

Kenneth presents three concrete techniques for managing software complexity. All three build on each other and are used in practice in every serious software project.

1. Choose the right design goals

The first thing you do in a project is choose 2–3 design goals — top-level quality objectives the system must satisfy. Kenneth is explicit: you cannot achieve all design goals simultaneously. Some are in conflict.

Design goal examples — and conflicts between them
Efficiency
The system uses minimal resources (CPU, memory)
Reliability
The system does not crash and produces correct results
Maintainability
Easy to change and maintain over time
Portability
Can run on different platforms/OS
Usability
Easy for end users to use
⚠ Efficiency vs Reliability
Performance optimisation often increases code complexity → more bugs
Kenneth: «Some of the design goals may be conflicting with one another. That's why it's not possible to achieve all of them at the same time.»
The rule from the lecture

«You have to choose two or three or four most appropriate design goals at the very beginning of the project. If the client tells you they want the system to be efficient and reliable, those have to be the design goals. Having clear design goals reduces the complexity of designing the system, because you know exactly what you need.»

2. Modularity and incremental development

Kenneth: «There is a limit to human understanding. When building a large software system, we apply divide and conquer — divide the large system into many smaller pieces and build one small piece at a time.»

A module is «a part of the system that makes sense to consider separately.» Modules interact with each other, but we can design and build them one at a time. The result:

  • More team productivity — one team focuses on one thing at a time
  • Fewer bugs — narrower focus means better oversight
  • More maintainable software — changes are isolated
  • More predictable development — easier to estimate time and cost for a single module

3. Information hiding — abstraction and encapsulation

The third technique is to use interfaces between modules. Kenneth explains: «When we access a module, we are only allowed to interact with it via interfaces.» Using an interface achieves two things at once:

Abstraction

We skip details. To use a module you do not need to understand what is inside it — only how the interface works.

Kenneth: «Abstraction means we skip details. You only have to understand how to use the interface — not the source code and implementation within the module.»

Encapsulation

Changes stay inside the module. When you maintain or change a module, it does not affect the others.

Kenneth: «Encapsulation means if we want to maintain a module, it's going to be just within this module. We don't have to touch the other modules.»

The key distinction

Abstraction is about using something without understanding its internals. Encapsulation is about changing something without affecting the outside. Both are achieved through interfaces, but they are different concepts. This question appears on the exam.

3

What is Software Engineering — and what is it not?

Kenneth and the Apple engineer in L1-3 agree: software engineering is much more than coding. In fact, coding takes only a fraction of a software engineer's time.

Programming in the small vs programming in the large

Programming in the small = coding. One developer writes code line by line. This is CS — the domain of computer science.

Programming in the large = software engineering. Coordinating an entire system and an entire team. This is SE — the domain of software engineering.

Kenneth: «Apart from coding, there are many things you have to do within software engineering.»

What does a software engineer do beyond coding?

  • Communicate with clients and users — on the application domain's terms, not programming's
  • Translate vague requirements into precise ones — a client rarely states exactly what they need
  • Build models — at different abstraction levels to communicate with different stakeholders
  • Choose and apply development processes — waterfall, agile, spiral etc. (covered in module 5)
  • Make design choices and trade-offs — there is rarely one correct solution
  • Work as a team — coordination, communication, code review

SE vs CS — the central distinction

From L1-3: «Both majors try to solve real world problems using code, but how they go about that is very different.»

Computer Science vs Software Engineering
Dimension Computer Science Software Engineering
Primary goal Understand algorithms and theory Design and build quality systems
Success means… Scientific breakthroughs Avoiding engineering failure
Focus Foundational algorithmic theory and data structures Best-practice principles for large systems
View of technology Understand and advance the technology Choose the right technology for the system
Scale «Programming in the small» «Programming in the large»
The analogy Scientist — builds to discover something new Engineer — learns in order to build quality products

Characteristics of software engineering (from Kenneth's summary)

Disciplined

We develop in a disciplined way — not ad hoc as in a programming assignment. Planning, process and documentation are mandatory.

Built-in quality

Quality is built in from the start — not something we «test in» at the end. SE tries to achieve quality throughout the entire process.

Team effort

Large systems require teams. Kenneth: «You don't sit in a cube and write code in a corner. You're always working with people.»

Multi-version

Software lives over time and has many versions. Requires configuration management and documentation to track changes.

Key Distinctions — summary table

The three distinctions below are the most common exam topics from module 1. Know these well and you are well prepared.

The three key distinctions from module 1
Concept pairAB
Abstraction vs Encapsulation Abstraction: use a module without knowing its internals — skip details Encapsulation: change a module without affecting the rest — isolate changes
CS vs SE CS: understand algorithms and theory — programming in the small SE: build quality systems in teams — programming in the large
Small vs Large Small: coding — one developer, one function, one file Large: engineering — process, models, team, version control
SE is four activities, not one

Kenneth summarises SE as four activities:

  • Modelling — requirements model (what) and solution model (how)
  • Problem-solving — not algorithmic, but systematic — there is no single correct answer
  • Knowledge acquisition — non-linear! You learn while you build, and sometimes you have to start over
  • Rationale management — document WHY decisions are made, not just what. Technology changes, and you need to be able to look back and understand the choices that were made
Ex 1

Identify complexity sources and design goals

▾

Scenario: A hospital wants a new patient records system. The client is the hospital director who knows nothing about programming. The system must handle hundreds of thousands of patient records and be available 24/7. The budget is limited.

  • a) Which of the four sources of software complexity are present here, and why?
  • b) Choose 2–3 design goals and justify your choice. Are any of them potentially in conflict?
  • c) What is meant by the «1 line per minute» problem? Relate it to this example.
Solution

a) Complexity sources:

  • Application domain: Developers are not medical experts. They must learn about HIPAA, ICD codes, clinical workflows etc. before they can build the system.
  • Communication: The hospital director talks about «patient history» and «diagnosis codes» — the developer thinks about database tables. Different vocabulary, different backgrounds.
  • Project management: 24/7 requirements, integration with laboratory systems, X-rays, prescription systems — many parts that must be coordinated.
  • Coding: Security mechanisms, encryption of patient data, high concurrency — all technically complex.

b) Design goals:

  • Reliability: A hospital system that crashes can cost lives. Absolute top priority.
  • Security: Patient records are sensitive information. Legally required.
  • Usability: Doctors and nurses do not have time for complicated interfaces.
  • Possible conflict: Security vs Usability — strict authentication requirements can make the system cumbersome in emergency situations.

c) 1 line per minute: If the system needs 500,000 lines of code and a team of 5 engineers produces 120,000 lines/year per person, it takes ~1 year. But planning, testing and communication reduce output — actual productivity is much lower than 1 line/min for safety- and medically-critical code.

Ex 2

Abstraksjon vs innkapsling — forklar med eksempel

▾

Du bruker funksjonen sort(liste) i et program. Du vet at den sorterer listen, men ikke om den bruker Quicksort, Mergesort eller Heapsort internt.

  • a) Hvilken av de to — abstraksjon eller innkapsling — demonstrerer denne situasjonen? Forklar.
  • b) Neste uke endrer bibliotekutvikleren intern implementasjon fra Mergesort til Timsort. Du merker ingenting i koden din. Hvilken av de to illustrerer dette?
  • c) Hva er grensesnittet i dette eksempelet? Hva er implementasjonen?
Løsning

a) Abstraksjon. Du bruker modulen (sort-funksjonen) uten å kjenne innsiden. Du hopper over detaljer om implementasjonen. Kenneth: «Abstraction means we skip details. You only have to understand how to use the interface.»

b) Innkapsling. Endringen skjedde inni modulen uten å påvirke resten av systemet. Du trenger ikke endre koden din. Kenneth: «Encapsulation means if you want to maintain a module, it's going to be just within this module.»

c) Grensesnitt = funksjonssignaturen sort(liste) → sortert liste. Implementasjon = den faktiske sorteringsalgoritmen (Mergesort/Timsort/osv.) og kildekoden inni funksjonen.

Ex 3

CS vs SE — klassifiser aktivitetene

▾

Klassifiser hver aktivitet som primært CS (programming in the small) eller SE (programming in the large):

  • a) Optimalisere en sorteringsalgoritme fra O(n²) til O(n log n)
  • b) Intervjue sykehusledere for å forstå arbeidsflyten i pasientinnleggelse
  • c) Bestemme at systemet skal bruke Scrum med 2-ukers sprints
  • d) Implementere en binærsøk-funksjon i Python
  • e) Designe grensesnittene mellom fem team som jobber på ulike moduler
  • f) Bevise at en graf-algoritme er korrekt for alle mulige input
Løsning
  • a) CS — algoritmisk optimalisering, Big-O-analyse. Typisk CS-aktivitet.
  • b) SE — kravinnsamling fra domeneeksperter. Kommunikasjon, ikke koding.
  • c) SE — valg av utviklingsprosess. Prosjektledelse og planlegging.
  • d) CS — programmering av én konkret funksjon. Programming in the small.
  • e) SE — grensesnittdesign mellom moduler er information hiding i praksis.
  • f) CS — korrekthetsbevising er theoretical computer science / algoritmeteori.

Merk: i praksis gjør en software-ingeniør begge deler. Distinksjonen er analytisk — hva er primærfokuset for aktiviteten?
