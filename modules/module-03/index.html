1

Association Class — when the association itself has attributes

Sometimes it is not enough to simply connect two classes with an association — the link itself has its own properties. Kenneth introduces this with an example: we want to record a grade when a student enrols in a course.

The problem: three failed attempts

❌ Option 1

Grade as an attribute under Student

Does not work: we don't know how many courses a student takes — we don't know how many grade attributes we need.

❌ Option 2

Grade as a multi-value attribute

Does not work: a list of grades does not tell us which grade belongs to which course — no mapping.

⚠️ Option 3

Association class

Better — but has one critical limitation. See below.

Association class — what it is and how to draw it

An association class is a class attached to the association line itself (not to either of the two classes). It is used when the association itself has attributes. Grade belongs to the link between student and course — not to student alone and not to course alone.

Association class med «Enrolls In» og grade-attributt
Association class attached to the association line with a dashed line — grade belongs to the link, not to Student or Course alone.
The critical limitation — Kenneth's own example

Kenneth gives this example: «Kenneth takes COM3111, fails (F). Next semester he takes COM3111 again and gets A+. Can we store both?»

No. The rule is: one pair of instances can only have one link. Kenneth and COM3111 are already linked — we cannot link them again with a different link. We can only store one of the two grades.

Kenneth: «Once a pair of instances are related, they are related. We cannot relate the same pair of instances using two different links.»

Consequence: association class is not suitable when a student can take the same course more than once.

The solution: introduce an Offering class

Instead of the student taking a course directly, the student takes an offering of the course. A course can have many offerings (one per semester). This means Kenneth is linked to two different offerings, not twice to the same course.

Offering-modellen: historisk data bevares
Student takes a specific Offering — not the course directly. Now Kenneth can be linked to two different offerings and both grades can be stored.
Rule of thumb: when to use association class
  • The association between two classes has its own attributes
  • And a pair of instances will never be linked more than once

If a pair of instances can be linked more than once (e.g. student takes the same course twice) → use an intermediate class like Offering instead.

Generalization and Inheritance

Generalization (inheritance) is the relationship between classes of the same type. We use a hollow triangle in UML to show that one class is a specialization of another. There are two directions to think about:

Specialization (top-down)

Start with a general class (Account). Notice that some attributes only apply to certain types — serviceCharge only for CheckingAccount, interestRate only for SavingsAccount. Specialize down into subclasses.

Kenneth: «We can see there is a discriminator — accountType — to discriminate account into two different types.»

Generalization (bottom-up)

Notice that two classes (BankAccount and CreditCard) share very similar attributes and operations. Extract a common superclass. Move shared things up.

Kenneth: «We can see that they are kind of similar objects — then we can perform generalization and create a more general class.»

Bank example: Account hierarchy with generalization
Account (italic = abstract) is specialized into CheckingAccount and SavingsAccount. CheckingAccount overrides withdraw() from the superclass.

Benefits of generalization

Kenneth summarizes: «We can extract the common attributes, relationships, and operations and put them in the superclass. They will be shared by the subclasses. This reduces redundancy of description and promotes reusability.»

  • Define once — common attributes and operations in the superclass are shared by all subclasses automatically
  • Easier changes — change in the superclass and all subclasses receive the update
  • Overriding — a subclass can override an operation from the superclass. withdraw() in CheckingAccount is then used instead of withdraw() in Account
  • Abstract class (italic) — no direct instances. All instances are of a subtype. Used for modeling purposes.
Inheritance depth limit

Kenneth: «Try to limit the level of inheritance to only two or up to three levels. If you have four, five or six levels of inheritance, it's going to make your diagram very difficult to read.» Keep it simple and readable.

Multiplicity in generalization — use notes

Example: PG students take 0–3 courses, UG students take 1–5 courses. Instead of two separate associations: relax to 0..5 at the Student level, and add a UML note for the specific constraints. Kenneth: «You can always provide additional information using a note.»

Generalization constraints: disjoint, overlapping, complete, incomplete

When drawing a generalization hierarchy, we MUST specify two types of constraints — one for overlap and one for completeness. These are written in curly braces at the generalization triangle: e.g. {disjoint, complete}.

Part 1: Can an instance belong to more than one subclass?

{disjoint}

An instance can belong to only one subclass — not both.

Kenneth's example: Account can be Personal or Business — never both. An account is either for a private person or a company.
{overlapping}

An instance can belong to multiple subclasses simultaneously.

Kenneth's example: A Player can play Tennis and Soccer at the same time. Part of the circle overlaps. It is possible to belong to both subclasses.

Part 2: Are all subclasses listed?

{complete}

All subclasses are listed. There are no other types beyond those shown.

Example: The university has only UG and PG students. «That's it» — Kenneth. No other student types exist.
{incomplete}

There may be other subclasses that are not modeled.

Example: A Tree can be pine, birch, oak — but there are many other tree types. The model is not exhaustive.
Kenneth's example: paying tuition fees — what is the correct constraint?

Scenario: Students can pay tuition with: Cash, Credit Card, or Debit Card.

Overlapping or disjoint? → Overlapping. You can pay part with cash and the rest with a credit card. Both subclasses can apply.

Complete or incomplete? → Incomplete. There are other payment methods — e.g. online banking — not listed.

Correct constraint: {overlapping, incomplete}

Exam strategy: step by step
  • Step 1: Ask: «Can an instance belong to more than one subclass?» → Yes = overlapping, No = disjoint
  • Step 2: Ask: «Are all possible types represented in the diagram?» → Yes = complete, No = incomplete
  • Step 3: Combine: write e.g. {disjoint, complete} at the triangle

Tilleggsbegrensninger og class diagram sammendrag

Kenneth dekker tre ytterligere begrensninger vi kan legge på class diagram. En constraint er en påstand som enten er sann eller usann, og som systemet MÅ håndheve.

Klikk på en begrensning for å lese forklaring og eksempel:

{ordered}
Ordnet rekkefølge
{subset}
Delmengde
{xor}
Exclusive Or
Klikk på en begrensning ovenfor for forklaring og eksempel.
{xor}-eksempel: Account holdes av Person ELLER Company
{xor}-begrensning: stiplet linje mellom de to assosiasjonene viser at nøyaktig én gjelder.

Sammendrag: alle class diagram-elementer

Ex 1

Association class vs mellomklasse — når bruker du hva?

▾

Scenario A: Et firma vil holde styr på hvilke ansatte som er med i hvilke prosjekter. Hvert (ansatt, prosjekt)-par har en attributt role : String (f.eks. «developer», «tester»). En ansatt kan bare ha én rolle per prosjekt, og kan ikke jobbe på samme prosjekt to ganger.

Scenario B: Et bibliotek vil holde styr på utlån. Samme bok kan lånes av samme person flere ganger (ulike datoer). Hvert utlån har attributter borrowDate og returnDate.

For hvert scenario: bruk association class eller introduser mellomklasse? Begrunn svaret.

Løsning

Scenario A — Association class er riktig.

  • Assosiasjonen (Employee–Project) har en attributt (role)
  • En ansatt kan bare ha én rolle per prosjekt → ett par instanser kobles maks én gang → begrensningen brytes ikke
  • Tegn en association class «Assignment» med role : String koblet til enrolls-assosiasjonen

Scenario B — Mellomklasse (Loan) er nødvendig.

  • Samme person kan låne samme bok mer enn én gang → ett par instanser kobles flere ganger
  • Association class tillater ikke dette — «once related, they are related»
  • Løsning: introduser klassen Loan med borrowDate, returnDate. Person tar en Loan, Loan er av en Book. Nå er person koblet til to ulike Loan-instanser for samme bok.
Ex 2

Tegn et generaliseringshierarki for et universitetssystem

▾

Scenario: Fra applikasjonsdomenet vet du følgende om et universitetssystem:

  • Alle brukere (User) har username og password
  • Studenter er enten UG (bachelor) eller PG (master/phd) — ingen andre typer
  • En UG-student kan ta 1–5 kurs, en PG-student kan ta 0–3 kurs
  • Lærere kan undervise i mange kurs, og en lærer kan også være student (doktorgrads-student)
  • Det finnes kun studenter og lærere som brukertyper i systemet

Tegn class diagrammet. Husk: klassenavn, constraints på generalisering, multiplicity og UML-notes der det trengs.

Løsning

Hierarki: User (abstract, italic) → {Student, Teacher}

  • User → Student, Teacher: {disjoint, complete} — en bruker er enten student eller lærer (men se merknad!), og det finnes ingen andre typer
  • Student → UGStudent, PGStudent: {disjoint, complete} — kun disse to typene
  • User er abstract (italic) — ingen direkte User-instanser
  • Student er abstract (italic) — alle instanser er enten UGStudent eller PGStudent

Assosiasjoner:

  • Student enrolls in Course: multiplicity 0..5 på Student-siden (relax fra 1..5/0..3 fordi det må gjelde alltid)
  • UML-note: «UGStudent: 1..5 courses. PGStudent: 0..3 courses»
  • Teacher teaches Course: * på begge sider

Merknad om doktorgradsstudent-lærer: Overlapping? Kenneth sier at hvis en lærer KAN være student, kan vi endre User-hierarkiet til {overlapping, complete}. Alternativt introduser en separat PhDStudent-klasse under PGStudent. Avhengig av domenebeskrivelsen.

Ex 3

Identifiser riktig generaliseringsbegrensning

▾

For hvert scenario: velg riktig kombinasjon av disjoint/overlapping og complete/incomplete. Begrunn valget.

  • a) Et kjøretøy er enten bil, motorsykkel, eller lastebil. Et kjøretøy kan kun tilhøre én type.
  • b) En person kan ha rollen som both Student og Employee ved samme institusjon. Det finnes også andre roller (f.eks. Alumni) som ikke er modellert.
  • c) Et dokument er enten Confidential eller Public. Det kan ikke være begge. Disse er de eneste to klassifiseringene som finnes.
  • d) Et måltid kan inneholde forrett, hovedrett OG dessert — eller bare noen av dem. Vi antar det finnes andre typer måltidskomponenter.
Løsning
  • a) {disjoint, incomplete} — kun én type (disjoint). Men det finnes andre kjøretøytyper som sykkel, scooter, osv. som ikke er modellert (incomplete).
  • b) {overlapping, incomplete} — kan tilhøre begge roller (overlapping). Alumni og andre roller eksisterer men er ikke modellert (incomplete).
  • c) {disjoint, complete} — kan ikke være begge (disjoint). Disse er de eneste to mulige klassifiseringene (complete).
  • d) {overlapping, incomplete} — et måltid kan ha flere komponenter samtidig (overlapping). Antatt at det finnes andre typer (incomplete).
