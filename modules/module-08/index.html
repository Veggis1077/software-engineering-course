Use Case Specification — the 8 components

A use case specification is a text document that precisely describes the flow of events within one use case. Kenneth says: «We have to specify what the system and the actor should perform within the use case.» Click each row to explore it in detail:

Use Case Name
Register for Courses
Required. Use present tense, active voice, from the actor's perspective. E.g.: «Register for Courses», «Withdraw Money», «Select Courses to Teach». Reflects what the actor does — not what the system does.
Brief Description
This use case describes how a student registers for courses for a given semester. It begins when the student chooses to register and ends when the schedule is confirmed.
Required. Short and precise — purpose and high-level overview. Include: what the use case does, who initiates it, and when it ends. Keep it to 2–4 sentences.
Participating Actors
Student (initiator), Billing System (secondary)
Required. List all actors — primary (the one who initiates) and secondary (other systems/actors that participate). The distinction between primary and secondary matters for the use case diagram (arrow vs plain line).
Preconditions
(only if necessary)
The student is logged in to the system.
Optional — only add if the use case CANNOT be performed without certain preconditions.

Kenneth: «A precondition is a statement about the state that the system and/or the actor must be in for the use case to be performed.»

Two critical rules:
  • Precondition states WHAT must be true — not HOW to make it true. Write: «Student is logged in», not «Student must log in by entering username and password».
  • Preconditions keep use cases independent of each other. You don't need to describe the login flow inside the Register use case — the precondition captures the requirement without coupling the two use cases.

ATM example: precondition for «Withdraw Money» → «Balance ≥ amount to withdraw». This states WHAT must be true, not an explanation of how the system checks it.
Flow of Events
Basic Flow + Alternative Flows (see below)
Required. Describe the sequence of actions — what the system and actor do. Always start with the basic flow (the normal path). Add alternative flows afterwards for exceptions, variants and optional behavior.

Basic flow is written as pseudo-code: if/then, while, repeat. Kenneth: «It's kind of like specifying the flow of events using pseudo-code.»
Postconditions
(only if important)
The student's schedule is confirmed and saved. The billing system has been notified.
Optional — only add when necessary. Kenneth: «A postcondition is only needed if the system state when the use case ends is important to an actor, OR if the completion leaves the system in a state that may need to be a precondition for another use case.»

ATM example: postcondition for «Withdraw Money» → «Balance is still non-negative after withdrawal.»

Purpose: helps stakeholders understand the outcome of the use case — especially important when the resulting state is not obvious.
Alternative Flows
A1, A2, ... An — see Section 2
Add as needed. Alternative flows describe optional, variant or exceptional behavior. They are numbered A1, A2, ..., An. Each alternative flow explicitly specifies where it resumes at the end. See Section 2 for a detailed walkthrough.
Non-Functional Req.
(only if relevant to this specific use case)
The registration must complete within 3 seconds.
Optional. Only non-functional requirements specific to this use case (e.g. response time for registration). General system-wide NFRs belong in the SRS, not here.
Precondition vs Postcondition — classic exam question

Precondition = state the system/actor MUST be in before the use case starts. States WHAT is true, not HOW it became true. Keeps use cases independent of each other.

Postcondition = state the system is in after the use case. Only necessary if that state matters to another use case, or is not obvious.

2

Extension Points and Alternative Flows

An extension point is a named place in the flow of events — a label — where alternative behavior can be inserted. Kenneth explains: «Extension points are primarily used for defining alternative flows — alternative, exceptional, or optional behavior within the use case specification.»

The three types of extension points

Single Location

The label appears exactly once in the specification. Example: «enter term» appears at only one place in the flow.

Discrete Locations

The label appears at two or more specific places. E.g.: «line passed» appears in the create activity AND in the modify activity.

Region

Defines a span between two extension points. Anything within the region can reference it. E.g.: from «begin modifying» to «confirm modifying».

The three types of alternative flows

Alternative flows are numbered A1, A2, ..., An. Click to explore the differences:

A1
Specific

Starts at one named extension point

A2
Bounded

Occurs between two extension points (region)

A3
General

Can start at any time in the flow

Click an alternative flow type for an explanation.
Last line of an alternative flow — required

Kenneth is explicit: «The last line of an alternative flow must specify the exit point of the flow — where the actor resumes the flow of events.»

  • Optional behavior → resume at the original extension point
  • Variant behavior → resume at a different extension point
  • Exceptional behavior → resume at original EP, a different EP, or the use case ends

Forget this line on the exam = wrong answer. Always specify it explicitly.

3

Subflows

A subflow is a segment of events within a use case that has a clear purpose and is atomic — extracted to improve readability. Kenneth: «By using subflow, we can improve the readability of a use case specification.»

Subflow — rules
  • Numbered S1, S2, ..., Sn
  • Give each subflow a descriptive name
  • No nesting — don't put subflows inside subflows
  • A subflow is not a separate use case — just a part of one
Subflow vs separate use case

Kenneth: «A subflow is not a separate use case. It's just part of the use case — a segment that is meaningful and has a clear purpose.»

Separate use case test: would you ever do just this step without the rest? If no → subflow.

Don't over-split — Kenneth's point

Kenneth warns against splitting too much: «Use cases do not directly communicate with each other. We assume use cases are intended to be independent of each other.»

Example of over-splitting: «Select Products», «Enter Order Info», «Enter Shipping Info», «Enter Payment», «Confirm Order» — all as separate use cases. Kenneth: «They are too small. They are simply part of the story, not the entire story.» Solution: Group everything into one «Place Order» use case and use subflows for the parts.

Test: «Would you ever do just one thing without doing the others? If you have to do other things together anyway, then why don't you group them together?»

How much detail is enough?

Kenneth's rule of thumb: «There should be enough detail so that all the stakeholders understand what's happening within the use case. The basic flow should unambiguously describe the required behavior. Keep asking yourself, what does this mean? — until all ambiguities have been resolved.»

Complete example — «Select Courses to Teach» (ASU)

Kenneth uses the ASU Course Registration System as a running example. Here is a complete use case specification with all elements — click the rows for explanations.

Use Case Name
Select Courses to Teach
Brief Description
This use case describes how a professor selects courses to teach for a term that has not started.
Participating Actors
Instructor (initiator)
Preconditions
The instructor is logged in to the system.
Flow of Events
See Basic Flow and Subflows below.
Postconditions
The instructor's selected courses are saved in the system.
Basic Flow
1.The use case begins when the Instructor chooses to select courses to teach.
2.The system displays the interface for selecting courses to teach.
3.The Instructor indicates the term and year. EP: enter term
4.When the Instructor has an activity to perform:
4a.If the Instructor chooses to create a schedule: S1: Create Schedule
4b.If the Instructor chooses to modify a schedule: S2: Modify Schedule
5.The system saves the selected courses. The use case ends.
S1: Create Schedule (Subflow)
1.The system retrieves and displays available course information for the given term, if the final date for changes has not passed. EP: line passed
2.The Instructor selects the courses he wants to teach.
3.The system records the selection. The subflow ends.
S2: Modify Schedule (Subflow)
1.EP: begin modifying schedule The system displays the instructor's current schedule.
2.The Instructor makes changes to the schedule.
3.EP: confirm modifying schedule The Instructor confirms changes. The subflow ends.
A1: Wrong Term/Year Entered (Specific Alternative Flow)
At enter term, if the Instructor entered the wrong term or year:
1.The system informs the Instructor that the term or year is invalid.
2.The flow of events resumes at enter term.
A2: Schedule Already Exists (Bounded Alternative Flow)
Between begin modifying schedule and confirm modifying schedule, if a schedule already exists:
1.The system displays a popup informing the Instructor that a schedule already exists.
2.The flow of events resumes at select activity.
Extension points are marked EP. Subflows are marked S1/S2. Notice that each alternative flow explicitly states where the flow resumes (green text).
Ex 1

Write a use case specification for «Withdraw Money» (ATM)

▾

Scenario: Write a complete use case specification for the use case «Withdraw Money» from an ATM system. Kenneth uses this example directly in the lecture.

  • The actor is a Bank Customer
  • The customer inserts the card, enters PIN, selects an amount and takes the cash
  • The system must check that the balance is sufficient
  • The system must update the balance after withdrawal
  • Alternative cases: wrong PIN, insufficient balance, customer cancels

Write: Use Case Name, Brief Description, Participating Actors, Precondition, Basic Flow (with at least one extension point), Postcondition, and at least two alternative flows (specify the type for each).

Solution

Use Case Name: Withdraw Money

Brief Description: This use case describes how a bank customer withdraws cash from an ATM. It begins when the customer inserts their card and ends when the cash is dispensed or the transaction is cancelled.

Participating Actors: Bank Customer (initiator), Banking System (secondary)

Precondition: The ATM is operational and connected to the banking system. (Kenneth's example: «Balance ≥ withdrawal amount» — but this is actually a condition checked during the flow, not a strict precondition.)

Basic Flow:

  • 1. The use case begins when the Customer inserts their card. [EP: card inserted]
  • 2. The system prompts for PIN entry.
  • 3. The Customer enters PIN. [EP: PIN entered]
  • 4. The system validates the PIN and displays the menu.
  • 5. The Customer selects Withdraw and enters the amount. [EP: amount entered]
  • 6. The system verifies sufficient balance and dispenses cash.
  • 7. The system updates the balance and ejects the card. The use case ends.

Postcondition: The customer's balance is reduced by the withdrawn amount. The balance remains non-negative. (Kenneth: «The balance must still be non-negative after the withdrawal.»)

A1 (Specific — Wrong PIN): At PIN entered, if the PIN is incorrect: the system displays an error. After 3 failures, the card is retained and the use case ends. Otherwise, the flow resumes at PIN entered.

A2 (Specific — Insufficient Balance): At amount entered, if the balance is less than the requested amount: the system displays an insufficient funds message. The flow resumes at amount entered.

A3 (General — Customer Cancels): At any time, if the Customer presses Cancel: the system ejects the card and discards all changes. The use case ends.

Ex 2

Identify the type of alternative flow

▾

For each alternative flow below: identify whether it is Specific, Bounded, or General. Justify your answer.

  • a) «At any time, if the network connection is lost, the system displays an error and the use case ends.»
  • b) «At confirm order, if the payment fails, the system prompts the customer to retry. The flow resumes at enter payment.»
  • c) «Between begin checkout and confirm checkout, if the shopping cart becomes empty, the system returns to the main page. The use case ends.»
  • d) «At select activity and modify schedule, if the deadline has passed, the system displays a message. The flow resumes at select activity.»
Solution
  • a) General — «At any time» is the classic phrasing for a general alternative flow. It can start at any point in the flow, not tied to a specific place.
  • b) Specific — «At confirm order» points to one specific extension point. First line: «At [EP], if [condition]» — typical specific.
  • c) Bounded — «Between begin checkout and confirm checkout» defines a region between two extension points. Classic bounded.
  • d) Discrete locations (Specific) — «At select activity and modify schedule» indicates a discrete locations extension point (appears at two places). The alternative flow type is still Specific (tied to named extension points, even though there are two).
Ex 3

Subflow or separate use case?

▾

Kenneth warns against splitting too much. For each scenario: decide whether it should be a subflow, a separate use case, or an alternative flow. Use Kenneth's test: «Would you ever do just this one thing without doing the others?»

  • a) «Enter Payment Information» som del av «Place Order»
  • b) «View Order History» — en student kan åpne dette uavhengig fra menyen
  • c) «Create Schedule» og «Modify Schedule» som deler av «Select Courses to Teach»
  • d) «System disconnects unexpectedly» som del av en hvilken som helst use case
Løsning
  • a) Subflow. «Enter Payment Information» har ingen mening alene — du ville aldri gjøre dette uten å faktisk plassere en ordre. Det er en del av historien, ikke hele historien. Kenneth: «They are simply part of the story, not the entire story.»
  • b) Separat use case. «View Order History» er en komplett, selvstendig funksjonalitet. Studenten kan gå direkte dit fra menyen uten å gjøre noe annet. Det er sin egen komplette historie.
  • c) Subflows S1 og S2. Kenneth bruker dette eksempelet direkte. «Create Schedule» og «Modify Schedule» er deler av «Select Courses to Teach». Du ville ikke gjøre en av dem uten konteksten fra use casen de tilhører.
  • d) General Alternative Flow. «System disconnects» er ikke en subflow (ikke et segment av normalflyten) og ikke en separat use case. Det er eksepsjonell atferd som kan skje når som helst — typisk general alternative flow. «At any time, if the connection is lost...»
