Use Case Specification

Lær å skrive presise use case-spesifikasjoner med basic flow, extension points, alternative flows og subflows — direkte fra Kenneth's forelesninger.

📖 4 seksjoner 🎯 10 quizspørsmål ✏️ 3 oppgaver ⏱ ~40 min
1

Use Case Specification — de 8 komponentene

En use case-spesifikasjon er et tekstdokument som presist beskriver flyten av hendelser innenfor én use case. Kenneth sier: «We have to specify what the system and the actor should perform within the use case.» Klikk på hver rad for å forstå den i detalj:

Use Case Name
Register for Courses
Obligatorisk. Bruk present tense, aktiv form, fra aktørens perspektiv. Eks: «Register for Courses», «Withdraw Money», «Select Courses to Teach». Reflekterer hva aktøren gjør — ikke hva systemet gjør.
Brief Description
This use case describes how a student registers for courses for a given semester. It begins when the student chooses to register and ends when the schedule is confirmed.
Obligatorisk. Kort og presis — formål og overordnet oversikt. Inkluder: hva use casen gjør, hvem som initierer den, og når den slutter. Hold det til 2–4 setninger.
Participating Actors
Student (initiator), Billing System (secondary)
Obligatorisk. List alle aktører — primær (den som initierer) og sekundær (andre systemer/aktører som deltar). Skillnaden mellom primær og sekundær er viktig for use case-diagrammet (pil vs linje).
Preconditions
(bare hvis nødvendig)
The student is logged in to the system.
Valgfri — bare legg til hvis use casen IKKE kan utføres uten visse forutsetninger.

Kenneth: «A precondition is a statement about the state that the system and/or the actor must be in for the use case to be performed.»

To kritiske regler:
  • Precondition sier HVA som må være sant — ikke HVORDAN gjøre det sant. Skriv: «Student is logged in», ikke «Student must log in by entering username and password».
  • Preconditions gjør use cases uavhengige av hverandre. Du trenger ikke beskrive login-flyten inne i Register-use casen — precondition fanger kravet uten å koble de to use casene.

ATM-eksempel: precondition for «Withdraw Money» → «Balance ≥ amount to withdraw». Dette er HVA som må være sant, ikke en forklaring av hvordan systemet sjekker det.
Flow of Events
Basic Flow + Alternative Flows (se nedenfor)
Obligatorisk. Beskriv sekvensen av handlinger — hva systemet og aktøren gjør. Start alltid med basic flow (normaltilfellet). Legg til alternative flows etterpå for unntak, varianter og valgfri atferd.

Basic flow skrives som pseudokode: if/then, while, repeat. Kenneth: «It's kind of like specifying the flow of events using pseudo-code.»
Postconditions
(bare hvis viktig)
The student's schedule is confirmed and saved. The billing system has been notified.
Valgfri — bare legg til hvis nødvendig. Kenneth: «A postcondition is only needed if the system state when the use case ends is important to an actor, OR if the completion leaves the system in a state that may need to be a precondition for another use case.»

ATM-eksempel: postcondition for «Withdraw Money» → «Balance is still non-negative after withdrawal.»

Formål: hjelper stakeholders forstå hva resultatet av use casen er — spesielt viktig når resultattilstanden ikke er åpenbar.
Alternative Flows
A1, A2, ... An — se Seksjon 2
Legg til etter behov. Alternative flows beskriver valgfri, variant eller eksepsjonell atferd. De nummereres A1, A2, ..., An. Hvert alternative flow spesifiserer eksplisitt where it resumes i slutten. Se Seksjon 2 for detaljert gjennomgang.
Non-Functional Req.
(bare hvis relevant for akkurat denne use casen)
The registration must complete within 3 seconds.
Valgfri. Kun ikke-funksjonelle krav som er spesifikke for denne use casen (f.eks. responstid for registrering). Generelle system-NFR plasseres i SRS, ikke her.
Precondition vs Postcondition — klassisk eksamensspørsmål

Precondition = tilstand systemet/aktøren MÅ være i før use casen starter. Sier HVA som er sant, ikke HVORDAN det ble sant. Gjør use cases uavhengige av hverandre.

Postcondition = tilstand systemet er i etter use casen. Bare nødvendig hvis tilstanden er viktig for en annen use case, eller ikke er åpenbar.

2

Extension Points og Alternative Flows

Et extension point er et navngitt sted i flyten av hendelser — en label — der alternativ atferd kan settes inn. Kenneth forklarer: «Extension points are primarily used for defining alternative flows — alternative, exceptional, or optional behavior within the use case specification.»

De tre typene extension points

Single Location

Labelen forekommer nøyaktig én gang i spesifikasjonen. Eksempel: «enter term» vises bare ett sted i flyten.

Discrete Locations

Labelen forekommer på to eller flere spesifikke steder. Eks: «line passed» vises i create activity OG i modify activity.

Region

Definerer et område mellom to extension points. Alt som skjer innenfor regionen kan referere til den. Eks: fra «begin modifying» til «confirm modifying».

De tre typene alternative flows

Alternative flows nummereres A1, A2, ..., An. Klikk for å utforske forskjellene:

A1
Specific

Starter ved ett navngitt extension point

A2
Bounded

Skjer mellom to extension points (region)

A3
General

Kan starte når som helst i flyten

Klikk på en alternativ-flow-type for forklaring.
Siste linje i alternative flow — obligatorisk

Kenneth er eksplisitt: «The last line of an alternative flow must specify the exit point of the flow — where the actor resumes the flow of events.»

  • Valgfri atferd → resume ved original extension point
  • Variant atferd → resume ved et annet extension point
  • Eksepsjonell atferd → resume ved original EP, et annet EP, eller use casen slutter

Glem denne linjen på eksamen = feil svar. Alltid spesifiser eksplisitt.

3

Subflows

En subflow er et segment av hendelser innenfor en use case som har et klart formål og er atomisk — man trekker det ut for å forbedre lesbarheten. Kenneth: «By using subflow, we can improve the readability of a use case specification.»

Subflow — regler
  • Nummereres S1, S2, ..., Sn
  • Gi hvert subflow et beskrivende navn
  • Ingen nesting — ikke legg subflows inni subflows
  • Et subflow er ikke en separat use case — bare en del av den
Subflow vs separat use case

Kenneth: «A subflow is not a separate use case. It's just part of the use case — a segment that is meaningful and has a clear purpose.»

Separat use case: ville du noen gang gjort bare dette trinnet uten resten? Hvis nei → subflow.

Ikke dele opp for mye — Kenneth's poeng

Kenneth advarer mot over-splitting: «Use cases do not directly communicate with each other. We assume use cases are intended to be independent of each other.»

Eksempel på feil: «Select Products», «Enter Order Info», «Enter Shipping Info», «Enter Payment», «Confirm Order» — alle som separate use cases. Kenneth: «They are too small. They are simply part of the story, not the entire story.» Løsning: Grupper alt til én stor «Place Order»-use case og bruk subflows for delene.

Test: «Would you ever do just one thing without doing the others? If you have to do other things together anyway, then why don't you group them together?»

Hvor mye detalj er nok?

Kenneth's tommelfingerregel: «There should be enough detail so that all the stakeholders understand what's happening within the use case. The basic flow should unambiguously describe the required behavior. Keep asking yourself, what does this mean? — until all ambiguities have been resolved.»

4

Komplett eksempel — «Select Courses to Teach» (ASU)

Kenneth bruker ASU Course Registration System som gjennomgående eksempel. Her er en komplett use case-spesifikasjon med alle elementer — klikk på radene for forklaringer.

Use Case Name
Select Courses to Teach
Brief Description
This use case describes how a professor selects courses to teach for a term that has not started.
Participating Actors
Instructor (initiator)
Preconditions
The instructor is logged in to the system.
Flow of Events
See Basic Flow and Subflows below.
Postconditions
The instructor's selected courses are saved in the system.
Basic Flow
1.The use case begins when the Instructor chooses to select courses to teach.
2.The system displays the interface for selecting courses to teach.
3.The Instructor indicates the term and year. EP: enter term
4.When the Instructor has an activity to perform:
4a.If the Instructor chooses to create a schedule: S1: Create Schedule
4b.If the Instructor chooses to modify a schedule: S2: Modify Schedule
5.The system saves the selected courses. The use case ends.
S1: Create Schedule (Subflow)
1.The system retrieves and displays available course information for the given term, if the final date for changes has not passed. EP: line passed
2.The Instructor selects the courses he wants to teach.
3.The system records the selection. The subflow ends.
S2: Modify Schedule (Subflow)
1.EP: begin modifying schedule The system displays the instructor's current schedule.
2.The Instructor makes changes to the schedule.
3.EP: confirm modifying schedule The Instructor confirms changes. The subflow ends.
A1: Wrong Term/Year Entered (Specific Alternative Flow)
At enter term, if the Instructor entered the wrong term or year:
1.The system informs the Instructor that the term or year is invalid.
2.The flow of events resumes at enter term.
A2: Schedule Already Exists (Bounded Alternative Flow)
Between begin modifying schedule and confirm modifying schedule, if a schedule already exists:
1.The system displays a popup informing the Instructor that a schedule already exists.
2.The flow of events resumes at select activity.
Extension points er markert EP. Subflows er markert S1/S2. Legg merke til at hvert alternative flow eksplisitt angir hvor flyten gjenopptas (grønn tekst).
Ex 1

Skriv en use case-spesifikasjon for «Withdraw Money» (ATM)

▾

Scenario: Du skal skrive en komplett use case-spesifikasjon for use casen «Withdraw Money» fra et ATM-system. Kenneth bruker dette eksempelet direkte i forelesningen.

  • Aktøren er en Bank Customer
  • Kunden setter inn kortet, taster PIN, velger beløp og tar ut pengene
  • Systemet skal sjekke at saldo er tilstrekkelig
  • Systemet skal oppdatere saldo etter uttak
  • Alternative tilfeller: feil PIN, utilstrekkelig saldo, kunden avbryter

Skriv: Use Case Name, Brief Description, Participating Actors, Precondition, Basic Flow (med minst ett extension point), Postcondition, og minst to alternative flows (spesifiser type for hvert).

Løsning

Use Case Name: Withdraw Money

Brief Description: This use case describes how a bank customer withdraws cash from an ATM. It begins when the customer inserts their card and ends when the cash is dispensed or the transaction is cancelled.

Participating Actors: Bank Customer (initiator), Banking System (secondary)

Precondition: The ATM is operational and connected to the banking system. (Kenneth's example: «Balance ≥ withdrawal amount» — but this is actually a condition checked during the flow, not a strict precondition.)

Basic Flow:

  • 1. The use case begins when the Customer inserts their card. [EP: card inserted]
  • 2. The system prompts for PIN entry.
  • 3. The Customer enters PIN. [EP: PIN entered]
  • 4. The system validates the PIN and displays the menu.
  • 5. The Customer selects Withdraw and enters the amount. [EP: amount entered]
  • 6. The system verifies sufficient balance and dispenses cash.
  • 7. The system updates the balance and ejects the card. The use case ends.

Postcondition: The customer's balance is reduced by the withdrawn amount. The balance remains non-negative. (Kenneth: «The balance must still be non-negative after the withdrawal.»)

A1 (Specific — Wrong PIN): At PIN entered, if the PIN is incorrect: the system displays an error. After 3 failures, the card is retained and the use case ends. Otherwise, the flow resumes at PIN entered.

A2 (Specific — Insufficient Balance): At amount entered, if the balance is less than the requested amount: the system displays an insufficient funds message. The flow resumes at amount entered.

A3 (General — Customer Cancels): At any time, if the Customer presses Cancel: the system ejects the card and discards all changes. The use case ends.

Ex 2

Identifiser type alternative flow

▾

For hvert alternative flow nedenfor: identifiser om det er Specific, Bounded, eller General. Begrunn svaret.

  • a) «At any time, if the network connection is lost, the system displays an error and the use case ends.»
  • b) «At confirm order, if the payment fails, the system prompts the customer to retry. The flow resumes at enter payment.»
  • c) «Between begin checkout and confirm checkout, if the shopping cart becomes empty, the system returns to the main page. The use case ends.»
  • d) «At select activity and modify schedule, if the deadline has passed, the system displays a message. The flow resumes at select activity.»
Løsning
  • a) General — «At any time» er den klassiske formuleringen for general alternative flow. Kan starte når som helst i flyten, ikke knyttet til et spesifikt sted.
  • b) Specific — «At confirm order» peker på ett spesifikt extension point. Første linje: «At [EP], if [condition]» — typisk specific.
  • c) Bounded — «Between begin checkout and confirm checkout» definerer en region mellom to extension points. Klassiisk bounded.
  • d) Discrete locations (Specific) — «At select activity and modify schedule» viser at det er en discrete locations extension point (forekommer på to steder). Alternative flowen er fortsatt av typen Specific (knyttet til navngitte extension points, selv om de er to).
Ex 3

Subflow eller separat use case?

▾

Kenneth advarer mot å dele opp for mye. For hvert scenario: avgjør om det bør være en subflow, en separat use case, eller et alternative flow. Bruk Kenneths test: «Would you ever do just this one thing without doing the others?»

  • a) «Enter Payment Information» som del av «Place Order»
  • b) «View Order History» — en student kan åpne dette uavhengig fra menyen
  • c) «Create Schedule» og «Modify Schedule» som deler av «Select Courses to Teach»
  • d) «System disconnects unexpectedly» som del av en hvilken som helst use case
Løsning
  • a) Subflow. «Enter Payment Information» har ingen mening alene — du ville aldri gjøre dette uten å faktisk plassere en ordre. Det er en del av historien, ikke hele historien. Kenneth: «They are simply part of the story, not the entire story.»
  • b) Separat use case. «View Order History» er en komplett, selvstendig funksjonalitet. Studenten kan gå direkte dit fra menyen uten å gjøre noe annet. Det er sin egen komplette historie.
  • c) Subflows S1 og S2. Kenneth bruker dette eksempelet direkte. «Create Schedule» og «Modify Schedule» er deler av «Select Courses to Teach». Du ville ikke gjøre en av dem uten konteksten fra use casen de tilhører.
  • d) General Alternative Flow. «System disconnects» er ikke en subflow (ikke et segment av normalflyten) og ikke en separat use case. Det er eksepsjonell atferd som kan skje når som helst — typisk general alternative flow. «At any time, if the connection is lost...»
